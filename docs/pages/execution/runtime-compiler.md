# Runtime Compiler

The JVM runtime compiler turns Wasm into JVM bytecode during instantiation.
That makes sense for long-lived JVM hosts where a module is executed often
enough to pay back compilation cost.

Add the JVM compiler artifact when runtime compilation is part of the host:

```kotlin
dependencies {
    implementation("uk.shusek.krwa:compiler")
}
```

Compile a machine factory once per parsed module when you expect to instantiate
the same module multiple times:

```kotlin
import uk.shusek.krwa.compiler.MachineFactoryCompiler
import uk.shusek.krwa.runtime.Instance

val machineFactory = MachineFactoryCompiler.compile(module)

val instance = Instance.builder(module)
    .withMachineFactory(machineFactory)
    .build()
```

Runtime compilation has a different risk profile from interpretation:

- generated bytecode must be loaded into the JVM,
- compiler cache directories need the same care as other executable artifacts,
- bytecode generation can amplify resource usage on hostile inputs,
- modules that require interpreter-only runtime features must stay interpreted.

The builder exposes the operational switches:

```kotlin
import uk.shusek.krwa.compiler.InterpreterFallback
import uk.shusek.krwa.compiler.MachineFactoryCompiler

val machineFactory = MachineFactoryCompiler.builder(module)
    .withInterpreterFallback(InterpreterFallback.FAIL)
    .withInterpretedFunctions(setOf(3, 8))
    .compile()
```

Use `InterpreterFallback.FAIL` when mixed compiled/interpreted execution would
hide an unsupported compiler path. Use `WARN` or `SILENT` only when fallback is
an expected compatibility tradeoff.

For untrusted code, start with the interpreter and add compilation only after
measuring the workload and setting resource limits around module loading and
execution. See also [CPU limits](cpu-limits.md) and
[compiler cache](compiler-cache.md).
